# BharatPravah 🚦

## AI-Based Adaptive Traffic Intelligence & Signal Decision-Support System

BharatPravah is an AI-powered traffic intelligence prototype that uses existing CCTV/video feeds to analyze traffic conditions, estimate congestion, forecast short-term demand, and recommend adaptive signal timing.

The system combines **Computer Vision, Machine Learning, real-time traffic analytics, and a FastAPI backend** into an end-to-end traffic monitoring and signal decision-support workflow.

> Developed and demonstrated as a prototype for the **IIT Bombay Hackathon**.

---

## Why BharatPravah?

Conventional traffic signals often rely on fixed-time schedules even when traffic demand varies substantially across approaches.

BharatPravah explores a data-driven alternative:

* detect vehicles and pedestrians from traffic video,
* map detections to road approaches using predefined ROIs,
* estimate approach-wise traffic demand and congestion,
* recommend adaptive green-time allocation,
* forecast congestion over a short time horizon, and
* expose the resulting analytics through a web-based interface.

The goal is to make traffic management more **responsive, measurable, and data-driven** without requiring additional roadside sensing hardware in the prototype.

## Key Capabilities

### 1. Real-Time Traffic Detection

The prototype uses **YOLOv8** to detect traffic participants from video streams.

The vision pipeline extracts information such as:

* vehicle detections,
* pedestrian detections,
* bounding boxes,
* confidence scores, and
* approach-wise traffic counts.

This converts raw video into structured traffic observations that can be used by downstream decision modules.

---

### 2. ROI-Based Traffic Analysis

Each intersection is represented using predefined **Regions of Interest (ROIs)** corresponding to road approaches.

```text
                    NORTH
                      ↑
                      │
              ┌─────────────┐
              │     ROI     │
              │             │
WEST   ───────► INTERSECTION ───────► EAST
              │             │
              └─────────────┘
                      │
                      ↓
                    SOUTH
```

Detected objects are assigned to the relevant approach based on their position within the configured scene.

This allows raw detections to be converted into direction-wise traffic measurements.

---

### 3. Congestion Estimation

Observed traffic counts are transformed into normalized congestion scores representing relative traffic demand.

```text
0 ───────────────────────── 1
Low congestion          High congestion
```

These scores form the basis for both adaptive signal recommendations and short-horizon forecasting.

---

### 4. Adaptive Signal Recommendation

The recommendation engine reallocates green time according to observed traffic demand while respecting operational constraints.

Prototype parameters:

| Parameter                      |       Value |
| ------------------------------ | ----------: |
| Signal cycle                   |      90 sec |
| Baseline green split           | 45 / 45 sec |
| Minimum green constraint       |      20 sec |
| Recommendation update interval |     ~10 sec |
| Timing smoothing               |     Applied |
| Pedestrian weighting           |         0.5 |

The use of periodic updates and smoothing helps avoid unstable frame-by-frame changes caused by noisy detections.

> **Important:** BharatPravah is currently a **signal timing decision-support system**. It does **not** directly control physical traffic-signal hardware.

---

### 5. Short-Term Traffic Forecasting

The prototype includes a short-horizon forecasting component based on a **Random Forest Regressor**.

| Forecasting Component | Value                   |
| --------------------- | ----------------------- |
| Model                 | Random Forest Regressor |
| Forecast horizon      | 30 sec                  |
| Prediction target     | Congestion score        |

The forecasting module uses historical traffic metrics generated by the vision pipeline and is integrated with the FastAPI backend.

---

### 6. Multi-Site Traffic Intelligence

The prototype was evaluated across multiple traffic sites, including:

* Bangalore
* Delhi
* Kolkata

The architecture is intended to support site-specific traffic observations, metrics, recommendations, and forecasting.

## Results & Evaluation

The adaptive recommendation module was compared against a fixed-time baseline.

### Baseline

```text
Signal cycle      : 90 sec
Green split       : 45 / 45 sec
```

### Estimated Waiting-Time Improvement

| Location    | Estimated Improvement |
| ----------- | --------------------: |
| Bangalore   |              11.3063% |
| Delhi       |               5.1448% |
| Kolkata     |              11.8984% |
| **Maximum** |          **11.8984%** |

The prototype therefore showed a maximum improvement of **11.8984% (approximately 11.9%)** in the evaluated waiting-time proxy relative to the fixed-time baseline.

> **Evaluation note:** the reported waiting-time metric is an **estimated proxy derived from the congestion scores used by the prototype**. It is not a direct measurement of physical vehicle delay from deployed traffic-signal controllers.

### Forecasting Evaluation

The forecasting component uses a **Random Forest Regressor** to predict congestion over a **30-second horizon**. The model output is a predicted congestion score and the forecasting endpoint is integrated into the FastAPI backend.

No mAP, precision, recall, MAE, or RMSE values are reported here because those metrics were not recorded as part of the project evaluation.

## Engineering Challenges

### Challenge 1 — From Video Detections to Traffic Demand

Raw object detections do not directly represent intersection-level traffic demand.

The project therefore introduces an ROI-based mapping layer that converts detections into approach-wise counts and congestion scores.

```text
Video
  ↓
Object Detections
  ↓
ROI Mapping
  ↓
Approach Counts
  ↓
Congestion Scores
```

---

### Challenge 2 — Stable Signal Recommendations

A recommendation that changes every frame can be unstable in the presence of noisy detections.

The prototype addresses this using:

* minimum-green constraints,
* demand-based allocation,
* periodic updates, and
* timing smoothing.

The recommendation cycle is updated at approximately **10-second intervals** rather than reacting to every individual frame.

---

### Challenge 3 — Connecting Perception with Prediction

The system connects real-time computer vision with machine-learning forecasting through a common traffic-metrics layer.

```text
Real-Time Computer Vision
          ↓
Traffic Metrics
          ↓
Historical Data
          ↓
Feature Generation
          ↓
Random Forest
          ↓
30-sec Congestion Forecast
```

This creates a bridge between **real-time perception** and **short-term predictive analytics**.

---

## Decision-Support Logic

At a high level, the prototype follows this reasoning loop:

```text
Observe traffic
      ↓
Estimate demand
      ↓
Compare approach conditions
      ↓
Allocate green time
      ↓
Apply minimum-green constraints
      ↓
Apply timing smoothing
      ↓
Generate recommendation
```

An example interpretation is:

```text
Higher observed demand on Approach A
                ↓
Increase recommended green allocation
                ↓
Maintain minimum green on other approaches
                ↓
Apply smoothing
                ↓
Return stable recommendation
```

Pedestrian demand is incorporated through a **0.5 weighting factor** in the prototype recommendation logic.

## Limitations

This is a **prototype research/engineering system**, not a production traffic-control platform.

Current limitations include:

* performance depends on video quality, camera viewpoint, and scene configuration;
* ROI definitions are predefined for the prototype;
* waiting-time improvement is based on an estimated proxy rather than physical field measurements;
* adaptive outputs are recommendations rather than direct traffic-signal commands; and
* real-world deployment would require controller integration, safety validation, infrastructure compatibility, and field testing.
